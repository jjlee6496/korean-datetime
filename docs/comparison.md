# 라이브러리 비교: 같은 한국어 문장, 같은 기준 시각

2026-10-02, **default·nearest·Duckling·dateparser를 모두 같은 환경에서 재측정**했습니다. 정확도·검출률·오탐률·유형별 점수·속도와 자체 정답셋에 같은 네 항목을 사용합니다.

데이터 출처: AI허브(한국지능정보사회진흥원) [「시간 표현 탐지 데이터」](https://aihub.or.kr) Training. 원문과 파서 응답은 저장소에 포함하지 않습니다.

비교 버전과 설정:

- korean-datetime 1.0.0: `default` (`cycle=future`)와 `ParseOptions(cycle=Cycle.NEAREST)`. 나머지 옵션은 같습니다.
- [Duckling](https://github.com/facebook/duckling/tree/59a13ff87b1aa8be6b93d387244f8636b26185c5): 커밋 `59a13ff`, native 소스 빌드, 한국어·Time, `Options False`, `Asia/Seoul`.
- dateparser 1.4.3: `languages=['ko']`, `RELATIVE_BASE`, `PREFER_DATES_FROM='future'` (기존 비교 설정 유지).

표본과 채점 기준은 기존 `scripts/compare_libraries.py`를 유지했습니다. 설정별 점수를 합치거나 가장 좋은 결과만 고르지 않습니다. [환경·재현 절차·측정 기록](benchmarks/2026-10-02-native/README.md)

## A. 외부 데이터 (AI허브 Training 표본)

표현 유형별 최대 50개씩 뽑은 **327개 시간 표현**과 **시간 표현이 없는 200개 문장**입니다(추출 시드 20261001). 기준 시각은 문서 작성 시각입니다.
**값까지 정답인 비율**은 정답 표현을 찾고 정해진 값의 부분(연·월·일·시·분)이 일치한 비율로, 미검출도 오답입니다. 오전/오후가 문장에 없는 시각은 모든 항목에서 12시간 단위로 비교합니다.
위치 검출은 정답 위치와 겹치면 인정하고, 오탐률은 비시간 문장에서 시간 결과를 하나라도 낸 문장 비율입니다.

| 지표 | korean-datetime default | korean-datetime nearest | Duckling | dateparser |

| 값까지 정답 (미검출 포함) | 76.5% (250/327) | 82.3% (269/327) | 72.2% (236/327) | 7.6% (25/327) |
| 위치 검출률 | 94.5% (309/327) | 94.5% (309/327) | 98.2% (321/327) | 19.3% (63/327) |
| 비시간 문장 오탐률 ↓ | 2.5% (5/200) | 2.5% (5/200) | 12.5% (25/200) | 5.5% (11/200) |

`nearest`는 기본값을 대체한 결과가 아닌 별도 설정입니다. 표본의 59%가 뉴스이며, 과거 기사에서 생략된 날짜를 가장 가까운 날짜로 해석하는 설정이 유리할 수 있습니다. 이 표본에서는 `default`보다 19개를 더 맞혔고 검출 수·오탐 수는 같았습니다.

### 2026-10-08 korean-datetime 재채점 (기간·최근 N·분기 추가 후)

위 표는 2026-10-02 한 번의 측정 결과라 그대로 둡니다. 기간 값·최근 N·분기·영업일을 추가한 뒤 **같은 표본(SHA-256 동일)을 같은 채점 함수로 korean-datetime만 다시 채점**했습니다.
Duckling·dateparser는 입력과 버전이 같아 결과가 바뀌지 않으므로 다시 실행하지 않았습니다.

| 지표 | default (10-02 → 10-08) | nearest (10-02 → 10-08) |
|---|---:|---:|
| 값까지 정답 | 250 → 250 / 327 | 269 → 269 / 327 |
| 위치 검출 | 309 → **311** / 327 (기간 전후 21 → 23 / 27) | 309 → **311** / 327 |
| 비시간 문장 오탐 | 5 → 5 / 200 | 5 → 5 / 200 |

이 표본은 표현 유형(상대 일, 요일, 월·일 등)별로 뽑아서 이번에 추가한 기간 값('6개월')·'최근 3개월'·분기 표현이 거의 들어 있지 않습니다.
그 효과는 [옵션별 벤치마크](benchmark.md)의 전체 데이터 재현율·정밀도에서 봐야 합니다. 속도와 자체 정답셋(B)은 10-02 측정을 유지하며, korean-datetime 코드가 바뀌었으므로 다음 native 재측정에서 갱신해야 합니다.

### 실패 사례를 읽는 방법

아래는 기존 측정에서 관찰한 표현 조각을 풀어 쓴 설명입니다. 새로 측정한 점수나 원문 전체가 아니며, 개별 사례만으로 전체 성능을 판단하지 않습니다.

| 표현 / 상황 | 관찰된 한계 | 사용 시 의미 |
|---|---|---|
| 단독 `전날`, `하루 전날`, `이튿날` | korean-datetime은 선행 문맥 없이 날짜를 정하지 않아 놓칩니다. 이 표본에서는 Duckling이 정답을 얻는 경우가 있습니다. | 문맥 의존 표현까지 필요하면 앞 문장의 기준 날짜를 별도로 처리해야 합니다. |
| `2천 명분`, `1,573명` | Duckling이 인원 수의 일부를 시간으로 검출한 오탐이 있었습니다. | 숫자 검출 범위가 넓을수록 비시간 문장도 함께 평가해야 합니다. |
| `춘천`의 `천`, `일반` | Duckling이 낱말 조각을 시간으로 검출한 오탐이 있었습니다. | 한국어 단어 경계가 정밀도에 영향을 줍니다. |
| 연·월이 생략된 뉴스 날짜 | korean-datetime 기본 `FUTURE`는 지난 일을 미래로 해석할 수 있습니다. | `NEAREST` 열을 기본값과 분리해 비교하고, 실제 용도에 맞게 설정합니다. |

korean-datetime도 비시간 문장 오탐률이 2.5%로, 오탐이 없는 파서는 아닙니다. 이 표본은 Training에서 추출했으며 독립적인 미공개 테스트셋 성능으로 해석하지 않습니다.

## 속도

같은 Docker Linux arm64 컨테이너에서 네 항목을 순차 실행했습니다. Apple M4 Pro, 12 vCPU·8GB RAM, Python 3.11.2, GHC 9.0.2 (`-O2`, `+RTS -N1`)이며 amd64 에뮬레이션은 사용하지 않았습니다.
외부 표본 527건을 전체 1회 예열한 뒤 순서를 바꿔 5회 측정했습니다(항목당 2,635건). 자체 정답셋 607건은 별도로 채점하며 아래 속도에 섞지 않았습니다.

### 직접 호출: 파싱·결과 생성

입력 디코딩, 기준 시각 준비, HTTP, JSON 바이트 직렬화는 제외합니다. Python의 `to_dict` 등 결과 생성과 Duckling의 `force . toJSON`은 포함하므로 순수 핵심 알고리즘만의 비용은 아닙니다. 아래는 5회 측정값을 합친 결과입니다.

| 지표 | korean-datetime default | korean-datetime nearest | Duckling | dateparser |
|---|---:|---:|---:|---:|
| 중앙값 (ms/문장) | 0.163 | 0.173 | 0.218 | 0.199 |
| p95 (ms/문장) | 0.375 | 0.411 | 0.834 | 1.064 |
| 처리량 (문장/초) | 5,528 | 5,146 | 2,992 | 2,882 |
| 회차별 중앙값 범위 (ms) | 0.160–0.165 | 0.164–0.183 | 0.213–0.226 | 0.186–0.229 |

처리량은 측정 건수를 누적 측정 시간으로 나눈 값이며 병렬 서버 처리량이 아닙니다. dateparser는 미검출이 많아 빨리 끝나는 점도 함께 고려해야 합니다.

### 직렬화와 HTTP를 포함하면

| 측정 경로 | 중앙값 (ms) | p95 (ms) |
|---|---:|---:|
| korean-datetime default 직접 호출 + JSON 바이트 생성 | 0.166 | 0.381 |
| korean-datetime nearest 직접 호출 + JSON 바이트 생성 | 0.176 | 0.417 |
| Duckling 직접 호출 + JSON 바이트 생성 | 0.221 | 0.837 |
| dateparser 직접 호출 + JSON 바이트 생성 | 0.202 | 1.068 |
| Duckling HTTP 요청 + 응답 JSON 디코딩 | 0.450 | 1.141 |

HTTP는 같은 컨테이너의 `127.0.0.1` 서버를 Python urllib로 호출한 값입니다. 요청 본문 인코딩은 제외하며 HTTP 통신과 응답 디코딩은 포함합니다. 직접 호출과 HTTP 응답은 예열·자체 정답셋을 포함한 **3,769건 모두 JSON 값이 일치**했습니다. 별도의 추정 통신 비용을 빼서 직접 호출 시간을 계산하지 않았습니다.

기존 3~7ms는 Mac의 Python과 amd64 에뮬레이션 Duckling 서버를 HTTP로 비교한 값이라 이 표로 대체했습니다. 소스·빌드·아키텍처·호출 경로가 함께 바뀌었으므로 차이를 네트워크만의 영향으로 해석할 수 없습니다. 이번에도 공유 개발 머신과 가상화 환경을 사용했고 라이브러리별 출력 구조가 달라, 모든 환경에서의 속도를 보장하지 않습니다.

## B. 구성 표현 (자체 정답셋)

같은 네 항목으로 607건을 다시 채점했습니다. 기준 시각은 기존과 같은 **2026-10-01 14:30(목)**입니다. 이 데이터는 korean-datetime을 만들며 쓴 것이므로 **절대 성능이 아니라 지원 유형과 해석 정책의 차이**를 보는 용도입니다.

정답은 korean-datetime의 기본 해석 정책을 따릅니다. 따라서 `nearest`도 동일한 정답과 비교하며, 설정에 맞게 정답을 바꾸지 않습니다. 범위는 시작과 끝이 모두 맞아야 정답이며 기존 채점기의 끝 표기 관례 차이 허용을 유지합니다. '다음 주말' 같은 정책 차이도 오답으로 셉니다.

| 유형 (표현 수) | korean-datetime default | korean-datetime nearest | Duckling | dateparser |
|---|---:|---:|---:|---:|
| 전체 (607) | 100.0% | 93.2% | 54.5% | 23.6% |
| 상대 일·주·월 (178) | 100.0% | 96.6% | 48.3% | 19.7% |
| 기간 전후 (52) | 100.0% | 100.0% | 36.5% | 5.8% |
| 범위 (93) | 100.0% | 95.7% | 48.4% | 4.3% |

`nearest`는 외부 뉴스 중심 표본에서 유리했지만, 기본 정책을 기준으로 한 자체 정답셋에서는 566/607(93.2%)입니다. `default`의 100%는 내부 회귀 성적이며 한국어 일반 문장 정확도 100%를 뜻하지 않습니다.
